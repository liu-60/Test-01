# 修复后端 worker 启动器的 Shell 兼容性

`/app/backend/launch-worker.sh` 是一个被容器作为入口使用的后端 worker 启动器。它在某些镜像中由 `/bin/sh` 解释执行，但当前版本只在开发者本机的 Bash 环境里工作，并且在收到停止信号时不能可靠地管理子进程。

请修复 `/app/backend/launch-worker.sh`，不要修改其他文件。

## 必须保持的命令行接口

```text
/app/backend/launch-worker.sh [--log LOG_FILE] -- COMMAND [ARG...]
```

- `--log LOG_FILE` 是可选参数，只出现在 `--` 之前；省略时使用 `/tmp/backend-worker.log`。
- `--` 后面的 `COMMAND [ARG...]` 必须作为一个命令及其原始参数执行。参数中的空格、通配符和前导短横线不能被重新拆分或解释。
- worker 的标准输出和标准错误追加写入日志文件。
- 参数缺失或命令部分为空时，启动器返回退出码 `64`。

## 兼容性和进程行为

1. 脚本必须是可移植的 POSIX `sh`，可由 `/bin/sh` 和 `/usr/bin/dash` 解释执行；不能要求 Bash、数组、进程替换或其他未声明的 Shell 扩展。
2. worker 正常退出时，启动器必须返回相同的退出码。
3. 启动器收到 `SIGTERM` 或 `SIGINT` 时，必须把对应信号转发给直接 worker 一次，并继续等待 worker 的最终退出结果；如果先后收到两个不同的停止信号，两个信号都不能被静默吞掉。worker 如果自行处理信号并以普通退出码结束，启动器必须返回该最终退出码。
4. 转发停止信号后，最多等待 worker 1 秒；如果 worker 仍未退出，必须发送 `SIGKILL`，回收它，并返回退出码 `137`，不能无限等待。
5. 启动器退出后不能遗留仍由它启动的 worker 进程。
6. 不能通过安装新依赖、访问外部网络或修改测试来解决问题。

## 建议验证

- 分别用 `/bin/sh` 和 `/usr/bin/dash` 做语法检查并运行。
- 使用包含空格和通配符的参数验证参数保真。
- 使用会处理 `SIGTERM`/`SIGINT` 的短小 worker 验证信号转发、最终退出码和进程清理。
- 使用忽略停止信号的 worker 验证 1 秒优雅窗口、`SIGKILL` 超时兜底和 `137` 退出码。
- 验证普通成功、普通失败和参数错误路径。

除上述外，不要求改变后端 worker 的业务行为或命令行接口。
